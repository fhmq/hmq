# HMQ v3.0.0

This release refactors broker lifecycle, message delivery and clustering. It
removes the legacy router configuration and introduces opt-in embedded quorum
replication without an external coordinator. Existing tags, including the
historical 2019 `v2.0` tag, are preserved.

## Breaking Changes and Migration

- The Go module/import path is now `github.com/fhmq/hmq/v3`, matching the v3
  release tag. Update imports, or install the command with
  `go install github.com/fhmq/hmq/v3@v3.0.0` after publication.
- Go 1.27.3 or newer is required. CI and release builds read the version from
  go.mod; container builds use the same patched toolchain. Do not rebuild with
  Go 1.26.6, which is affected by reachable standard-library vulnerabilities.
- Plain MQTT now defaults to `127.0.0.1:1883`; the old CLI port was 8090 despite
  its help text saying 1883. Bind explicitly to expose the broker remotely.
  The container supplies an explicit `0.0.0.0:1883` binding inside its namespace.
- `router` and legacy cluster `host`/`port` configuration are rejected. Configure
  node/cluster IDs, static seeds and mutual TLS using `conf/cluster.md`.
- Direct-cluster handshake v3 is incompatible with earlier experimental
  handshakes. Upgrade all members together; each certificate needs exactly one
  node URI SAN, `urn:hmq:node:<ID>`.
- Durable files are identity-bound. Back up a node's complete state together;
  do not reset, exchange or independently restore Raft logs and delivery cursors.
  Incomplete or corrupt logs fail closed; there is no automatic old-router or
  memory-session migration.

## Architecture and Reliability

- Replace external router routing with authenticated broker-to-broker links.
  Default direct forwarding is best effort; experimental reliable mode adds
  local event/inbox receipt persistence without consensus.
- Add experimental `cluster.quorum`: one fixed embedded Raft partition,
  majority-commit publication acceptance, streamed mTLS snapshots and local
  committed-entry consumers. Followers can forward to the observed leader over
  authenticated cluster links; no separate coordination service is required.
- A QoS1 PUBACK in quorum mode follows commit and state-machine application,
  not subscriber acknowledgment. Internal retries reuse an operation ID and
  frozen payload. Timeouts and lost acknowledgments remain uncertain outcomes;
  client reconnects or crashes can produce duplicate deliveries.
- Bound quorum request counts, queued/pending bytes, worker counts and frames.
  Add context-aware sending, cancellation isolation and safe partial-frame
  teardown. Close admission before waiting for callbacks and in-flight work.
- Add standalone local WAL, inbox/outbox and session storage. Outbox compaction
  preserves its identity, pending order and sequence high-water mark.
- Add opt-in single-node ordinary persistent sessions with offline queues,
  durable outbound QoS state and a bounded recovery window. This mode is separate
  from quorum and does not replicate MQTT sessions.

## Fixes and Maintenance

- Correct connection takeover, subscription generation checks, outbound packet
  ownership, QoS ACK/retry ordering and shared-candidate handling.
- Strengthen listener, connection, worker-pool and bridge shutdown; preserve
  state across interrupted writes and reject stale connection-owned mutations.
- Harden authentication/ACL paths and connection notifications; avoid exposing
  credentials in monitoring or notifications.
- Add indexed pending scans and bounded batch rotation, including fixed cycle
  bounds so sustained new traffic cannot indefinitely starve old retries.
- Add cluster/reliable/quorum health endpoints with explicit local-state limits.
- Add the embedded Raft dependency, update compatible transitive dependencies
  and remove unused dependencies.

## Important Operational Limits

- Quorum currently supports ordinary non-retained QoS0/1 publications and clean
  online sessions only. QoS2, retained storage, shared subscriptions, wills,
  non-clean sessions and bridge plugins are rejected in this mode. Default
  memory-mode MQTT behavior is not replaced by enabling the new packages alone.
- This is not Kafka feature parity: there is no topic partition placement,
  dynamic membership/discovery, consumer offset API, replicated MQTT sessions or
  operational rolling-upgrade protocol.
- Configure full-mesh cluster seeds for forwarding to every possible leader.
  Raft and cluster forwarding use distinct ports. TLS member checks assume
  cooperating crash-fault peers, not Byzantine members.
- Publication/deduplication history and quorum delivery cursors have no automatic
  retention/compaction. The kernel has fixed accepted-entry/payload capacity;
  monitor disk, memory and health. Outbox compaction does not reclaim quorum,
  eventstore or inbox history.
- Experimental local session mode rejects inbound QoS2 and persistent shared
  subscriptions. CONNECT rollback still copies the session snapshot, so overall
  recovery memory is not independent of backlog size.
- Durable local storage currently supports Linux and macOS, not Windows. Windows
  artifacts support memory-only operation. Filesystem sync assumptions still
  apply; SIGKILL tests do not prove power-loss or hardware-failure durability.

## Verification

- Full uncached `go test -race -count=1 -timeout 180s ./...` regression.
- `go vet ./...` and `git diff --check`.
- `govulncheck` with Go 1.27.3 reports zero reachable and zero imported-package
  vulnerabilities. GO-2026-5932 remains a module-level match for the unmaintained
  `golang.org/x/crypto/openpgp` package, which HMQ does not import; it has no fixed
  upstream version. This is not a claim of zero module-level advisories.
- Real three-broker mTLS tests for commit-before-PUBACK, follower forwarding,
  response-loss deduplication, leader changes, majority loss and restart.
- Concurrent MQTT publisher ordering and replica convergence tests.
- Cancellation/partial-frame stress tests, session SIGKILL recovery, durable
  snapshot/store recovery and bounded-shutdown tests.
- Cross-platform build artifacts and SHA256 checksums are produced by the
  release workflow. See the published assets and workflow result for completion.

Read `conf/cluster.md`, `broker/QUORUM.md` and `broker/QUORUM_FORWARDING.md` before
enabling experimental cluster modes.
