# HMQ v4.1.1

This is the first published release of the v4.1 series and supersedes the
unpublished v4.1.0 tag. It corrects a test assumption about when an offline
member's delivery cursor allows history reclamation. Compaction safety rules
are unchanged: a majority can continue committing while reclamation waits
for all members' durable cursor reports.

## Highlights since v4.0.2

- Durable inbound and outbound QoS 2 for resumable standalone WAL and quorum
  sessions, including restart and node changes. MQTT 5 supports non-expiring
  durable sessions; finite session expiry timers are not implemented.
- A standalone SessionStorage interface for embedders, per-session message
  and byte quotas, and a capacity monitor at GET /api/v1/capacity.
- Quota rejection is atomic for durable fanout. If a queue fills after
  PUBREC, the pending exchange survives and no successful PUBCOMP is sent.
- Checkpoint durable session state, retain the replay suffix for lagging
  followers, and reclaim consumed Raft history and WAL space safely.
- Bound MQTT 3.x and 5 packet size before decoding, avoid allocating the
  advertised body for incomplete frames, and isolate slow consumers
  (issues #208, #177 and #178).

## Upgrading

Upgrade all quorum members together; the checkpoint peer protocol does not
support rolling upgrades from older versions. Back up the snapshots and both
Raft and delivery WALs together. Do not downgrade compacted storage. A member
that stops consuming can pin the reclamation point until it catches up.
Durable replay guarantees do not imply exactly-once business processing or
exactly-once transient socket delivery.

Kubernetes changes are not included. The local Docker Compose setup requires
a source checkout or source archive.
